# BranchForge：逐行三方合并内核

调用方直接提供同一文件的共同祖先 `base` 和两个分支版本 `ours`、`theirs`。
不实现仓库管理、提交存储或人工解决流程；冲突保留为结构化数据，不做标记渲染。

## API

```python
from branchforge import diff, merge, Edit, Conflict
```

- `diff(base: bytes, target: bytes) -> list[Edit]`
  返回把 `base` 变成 `target` 的编辑序列。`Edit(start, end, replacement)`
  给出基线行下标的左闭右开区间及替换字节；`start == end` 表示纯插入。
  删除行数加插入行数最小；没有保留行隔开的连续改动合并为一项。
- `merge(base: bytes, ours: bytes, theirs: bytes) -> list[bytes | Conflict]`
  返回按文件顺序排列的普通字节块（`bytes`）和冲突块（`Conflict`）。
  `Conflict` 保留基线行区间 `[base_start, base_end)` 及该范围对应的
  `base`、`ours`、`theirs` 原文，调用方无需重新计算差异即可展示冲突。

## 行模型

输入均为字节串，以 LF 分行，LF 属于该行；空串是零行，末行可以没有 LF。
行是否相等按完整字节判断；不归一化换行、不删除空白、不丢弃末行无 LF 状态；
输入中的冲突标记文本只视为普通内容。

## diff 决胜规则（确定性保证）

算法为 Myers O(ND) 贪心 frontier 扩展。当删除与插入能让对角线到达同样远的
基线位置时（`V[k-1] == V[k+1]`），优先选择删除（沿基线向右），其次插入，
随后尽可能跟随 snake（连续保留行）。行先映射为整数 id 再比较，整个过程
完全确定：同一输入永远产生同一编辑序列。

## 合并语义

- 两侧非空编辑区间有共同基线行时相碰；纯插入仅在位置严格落入另一编辑区间
  内部时与其相碰；两个纯插入在同一位置时相碰；区间仅首尾相接不算相碰。
- 冲突候选区域恰好覆盖相碰关系传递闭合后的最小编辑集合（并查集分组），
  不扩大范围，也不拆散传递相碰的编辑；只含一侧编辑的区域直接采纳。
- 对包含两侧编辑的区域，分别在该区域基线上重放各侧编辑；所得字节完全一致
  时只保留一次，否则输出一个 `Conflict`；未被编辑覆盖的基线内容保留在
  对应侧的区域原文中。
- 边界插入不与相邻替换制造冲突；输出时放在前一替换之后、后一替换之前。
  所有未相碰的变更都会出现在结果中。

## 性能

目标场景：每份输入 100000 行、不超过 10 MiB，两侧相对 base 合计最短编辑
成本不超过 200 行（含大量重复行）。diff 时间 O((N+M)·D)、回溯空间 O(D²)，
不生成与两份全文行数乘积同阶的状态。实测该场景合并约 0.6 s，
峰值额外内存约 19 MiB（上限 128 MiB，输入字节串不计入）。

## 测试

```sh
./run_tests.sh
```

- `tests/test_diff.py`：小输入上以独立的 LCS 动态规划参考实现判定 diff
  最短性，并验证重放后逐字节等于 target；随机用例使用极小行字母表以
  制造大量重复行（非手写例子）。
- `tests/test_merge.py`：构造一侧两个编辑被另一侧一个编辑串成同一区域、
  同位置插入、删除区间两端插入、末行无 LF 等场景，精确断言普通块与冲突原文。
- `tests/test_large.py`：可复现的 100000 行数据（短差异 + 大量重复行），
  实际运行合并并用 tracemalloc 测量峰值额外内存。
